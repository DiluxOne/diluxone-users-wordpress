# Architecture

How DiluxOne Users+ is built, the rules its code follows, and what a review of it looks for. This is the single source: people read it, coding agents read it (through [`AGENTS.md`](../AGENTS.md)), and the automated Claude review reads it on every pull request. When the code changes one of these facts, this file changes in the same pull request.

When in doubt, prefer the project's existing patterns over textbook WordPress patterns.

## What this repo is

A WordPress plugin that owns everything about the people who use a site: the fields they are asked for, how they sign in, the account area they see on the front end, their second factor, their sessions and their data. It depends on no other plugin.

**The distinguishing decision** is that the plugin knows nothing about the site it runs on. It does not know what a course is, or a membership, or a forum. Anything that belongs to another domain enters through a filter (`diluxone_users_sections`, `diluxone_users_summaries`, `diluxone_users_notification_prefs`) or through a shortcode pasted into a section. A pull request that teaches the plugin about LifterLMS, WooCommerce or bbPress is going the wrong way; the only exception is a `function_exists()`-guarded bridge, and there is exactly one today (`bbp_get_user_profile_url()` in `includes/handle.php`). The seams an add-on uses are public API, listed in [`extending.md`](extending.md).

The second decision worth knowing: **what an administrator turns off disappears from the front end, with no second switch to remember.** Sections declare an `available` callback; with no social provider enabled there is no "Linked accounts" section at all. A feature added without that wiring will show an empty screen to somebody.

Paid subscriptions are not part of this plugin. They drag in a payment gateway, recurring billing and invoicing, and will arrive as a separate add-on, so a free site does not carry billing code it never runs.

## Architecture quick-reference

Procedural, no classes, no namespace, everything prefixed `diluxone_users_` / `DILUXONE_USERS_`. Every file in `includes/` is independent and only registers hooks; they are loaded in alphabetical order by a `glob()` in the main plugin file, so **nothing may depend on load order**: if a file needs another to have run, that is a hook, not an ordering assumption.

| Area | Files |
|---|---|
| Main file: constants, the loader, activation | `diluxone-users.php` |
| Options, their defaults and where each is stored on a network | `options.php`, `options-scope.php` |
| Looks: the tokens the admin's answers become, the theme's colours, the short palette | `templates.php`, `theme-colors.php`, `theme-measure.php`, `palette.php` |
| User fields (definition, values, edit policy), and WordPress's own user meta keys no field may take | `fields.php`, `fields-forms.php`, `core-meta.php` |
| The required fields missing, asked after a sign-in | `fields-missing.php` |
| Account area, sections registry | `account.php`, `account-sections.php`, `account-security.php` |
| Sign-in: link, password, passwordless mode, the ways in, the page of its own | `login.php`, `login-ways.php`, `login-messages.php`, `passwordless.php`, `login-door.php` |
| Registration and password reset | `register.php`, `reset.php` |
| Two-step verification, and its screen on wp-login.php | `auth.php`, `auth-email.php`, `auth-wp-login.php` |
| The emergency switch (`DILUXONE_USERS_SAFE_MODE`) | `safe-mode.php` |
| The pages a cache must not keep | `no-cache.php` |
| Social login | `sso*.php` |
| Sessions, the client's address | `sessions.php`, `client-ip.php` |
| Activity log | `log.php`, `log-events.php`, `log-privacy.php`, `admin-log.php` |
| Networks: the hub's doors and the way back, the network's screens | `multisite.php`, `network-hub.php`, `admin-network.php` |
| Networks: membership — the policy, its queue, "by invitation", its screen | `membership.php`, `membership-join.php`, `admin-membership.php` |
| Privacy (export and erasure): confirmed signed in, carried out on confirmation, its e-mails | `privacy.php`, `account-confirm.php`, `account-export.php`, `account-closing.php`, `account-mail.php` |
| Notifications and mail | `notify.php`, `mail.php`, `mail-templates.php` |
| Admin screens | `admin*.php` |
| Removal of everything the plugin stored | `uninstall.php` |

Templates live in `templates/` and are overridable from the active theme at `wp-content/themes/<theme>/diluxone-users/<path>.php`, resolved by `diluxone_users_template()`. Styling is driven by `--diluxone-users-*` custom properties so a site can restyle the plugin by redefining values, without copying its stylesheet ([`extending.md`](extending.md#styling-it-from-a-site)).

## Hard rules

### Security (highest priority)

- **All AJAX endpoints** verify a nonce (`check_ajax_referer`) and, when the action is not part of signing in, that there is a session. A sign-in step cannot require a session, because it exists to open one: it carries the page's nonce all the same (made for nobody when nobody is signed in), checked first like every other step, and something single-use proves the sign-in.
- **Every handler that reads a request checks its nonce and its capability first, in the same function, before it reads anything else.** Not in the caller, and not after reading the id the nonce's action is built from: a nonce's action is fixed, and whose thing it is is the check after it. A panel's `save` starts with `check_admin_referer( 'diluxone_users_panel_' . $screen, 'diluxone_users_panel_nonce' )` written out in the save — Plugin Check, which is what wordpress.org runs, only sees WordPress's own nonce functions — and then `diluxone_users_panel_allowed()` (`diluxone_users_admin_cap()`), and so does a helper that reads the panel's form; the screen checks the same before calling it. A helper that only receives values reads none of the request (the Tools tab reads its form in `diluxone_users_tools_action()` and hands each tool what it needs). The `NonceVerification` suppressions left are for what cannot carry a nonce — a link from an e-mail, whose key is checked before anything is kept; WordPress's own sign-in form, vouched for by the password it just verified; the second step's pending-attempt key — and for reads that only pick what is drawn; each says which, and where the check is.
- **All `$_POST` / `$_GET` input** is unslashed and sanitized: `sanitize_text_field( wp_unslash( $_POST['x'] ?? '' ) )`, `sanitize_key`, `sanitize_email`, `wp_kses_post` for HTML. Raw superglobals are a defect.
- **All output** is escaped, at the line that prints it: `esc_html`, `esc_attr`, `esc_url`, `esc_textarea`, and `wp_kses( $html, diluxone_users_allowed_html() )` for markup the plugin built as a string (a pill, an icon, a tab drawn into a buffer). A template prints itself through `diluxone_users_template_part()`; it is not returned and echoed. There is no `phpcs:ignore` of `EscapeOutput` in the plugin and a new one is a defect: wordpress.org's review reads "escaped inside" as unescaped output, and DiluxOne's checks fail on it. `EscapedOutputTest` draws every screen and tab and proves the allow-list takes nothing out; an element the plugin starts printing goes into `diluxone_users_allowed_html()` in the same change.
- **All SQL** uses `$wpdb->prepare()`, with no exceptions. Where a table name has to be interpolated it comes from `$wpdb->prefix` and nowhere else.
- **Secrets are never logged and never stored in the clear.** Two-step codes, backup codes and the sign-in token are stored hashed (`wp_hash`). A pull request that stores any of them readable is a defect, not a simplification.
- **A single-use thing must be single use.** Sign-in links, the links of pending sign-ups, two-step codes, backup codes and WebAuthn challenges are consumed on first use. Removing the delete-after-use is a security regression even when it "fixes" a retry.
- **A social identity is handed an existing account only on the provider's explicit "verified".** Silence is not a yes there, whatever the settings say; for a new account an explicit "no" closes the door and the "verified only" setting decides what silence means (`diluxone_users_sso_email_trusted()`).

### Coherence: the rule that is specific to this plugin

- Anything shown to a person must be **true at the moment it is shown**. If a notice says the second step is not being asked for, that has to hold for every way into the site the administrator left open, not just the one the author had in mind. `diluxone_users_2fa_ways()` exists because that notice was wrong.
- A new section declares `available` and `why` if it can ever have nothing to show.
- A new setting that hides something on the front end actually hides it. Half-applied settings are the failure mode this plugin is trying to avoid.
- **The plugin never locks anybody out.** The second step always has somewhere to be answered (`diluxone_users_2fa_surface()`): the sign-in page when it is one a stranger can open (`diluxone_users_login_page_live()`: published, not private, no password, or the page of its own, `diluxone_users_door_open()`), otherwise wp-login.php (`includes/auth-wp-login.php`). With neither — no page, and a site that turned wp-login.php off with `diluxone_users_2fa_on_wp_login` — it is not asked, not offered in the account, and "required" is refused on save. A method ticked that nothing registers today (an add-on's, the add-on off) leaves the e-mail code in its place when it was the only one, so the step is still asked and a person who had only that method still gets in. Whom the step is for (`diluxone_users_2fa_in_scope`) and whether a sign-in may skip it (`diluxone_users_2fa_skip`) are everybody and never as far as the plugin goes; an add-on narrows the first and answers the second (Users+ Pro's roles and remembered browser), so without it nothing stored narrows or skips anything. And `DILUXONE_USERS_SAFE_MODE` (`includes/safe-mode.php`) is the way back in for an administrator: while it is true nothing redirects (wp-login.php takeover, the reset and privacy hand-offs, the hub's doors and forms, the page of its own, which `diluxone_users_door_open()` shuts while its rules stay, the dashboard profile), nobody is asked for the second step and social sign-in is shut (an add-on's way in asks the same and stands aside). A new redirect, door or step asks `diluxone_users_safe_mode()` and stands aside.
- **Activating the plugin changes nothing on the site, and the screens say so.** A setting nobody saved reads Not configured (`unset`, `diluxone_users_option_is_set()`, `diluxone_users_summary_row()`) on every summary, with what WordPress does meanwhile; no box is ticked and no option chosen for it; a group that depends on another answer waits for it, disabled, and the save leaves what it did not ask alone (`diluxone_users_ui_choices()`, `$waits`). A value saved equal to its default is a decision and reads as one. Every default leaves the site as WordPress has it, and every feature waits for an administrator: sign-in stays WordPress's (`diluxone_users_login_method` is `password`), the plugin opens no door to registration and adds nothing to wp-login.php's form (`diluxone_users_wp_register_fields`), two-step verification, the sessions list, the photo upload and the data requests in the account are off, the plugin's own notices are "never sent" (`diluxone_users_notice_rules`), a reset keeps the other sessions open (`diluxone_users_reset_ends_sessions`), the activity log records nothing (`diluxone_users_log_levels` is empty), a network's sites keep their own wp-login.php (`diluxone_users_network_hub`), and a session lasts what WordPress decides until a length is saved (0 is WordPress's). On a network the membership policy adds nobody until it is confirmed. Nothing is written on activation either: no setting (the starter fields — first and last name, neither required — are read from `diluxone_users_default_fields()` until a list is saved; the rest are suggested on User fields › Suggested fields), no log table and no purge event until a group is ticked (`diluxone_users_log_current()` makes the table only then), no rewrite rule until an account page is chosen, a social provider set up or the shape "A page of its own" chosen (`diluxone_users_rewrite_stamp()`), no Access column, profile block or admin stylesheet on WordPress's Users screens until a way in they describe is on (`diluxone_users_access_features_on()`), no extra field on the profile screens but the site's own, nothing written into WordPress's session records until the sessions list is on, no device noted until the new-device notice is sent, and no note of the site's mail until the plugin sends mail of its own. `make test-noop` fingerprints a clean site before and after activation and fails on any difference. Users+ Pro follows the same rule: activating it beside the free plugin turns on no policy, method, layout, section or network, and writes nothing (its own `make test-noop`).
- **With Colours › the theme's, the colours are the theme's of the moment, dark mode included.** What the palette cannot say is measured in the visitor's browser (`assets/diluxone-users-theme-measure.js`), measured again when the system's colour scheme changes or the theme's own switch changes a class, a `data-theme` or a style on `<html>` or `<body>`, and kept once per scheme (`…:light`, `…:dark`), so the early script (`diluxone_users_measure_early()`) starts a dark page with what was measured on a dark one. A shade of the account area's ground is then mixed from the measured surface and text (`diluxone_users_ground_tint()`), not printed as its light hex. The plugin has no dark mode of its own: dark mode is the site's.
- A registration that did not come through a form carrying the plugin's fields (`registration_errors` with neither the fields' nonce nor any field) is not checked for them; once a field is posted, the nonce has to verify.
- **Every door says `wp_login`.** The plugin's own doors open the session through `diluxone_users_open_session()`, which fires WordPress's `wp_login` once, then `diluxone_users_logged_in`. While it fires, the plugin's own listeners on `wp_login` — the second step, the password's announcement, the way back on a network — stand aside (`diluxone_users_own_door()`), so nothing is asked twice and the log has one row.
- **The required fields an account came in without are asked after the sign-in, not instead of it** (`includes/fields-missing.php`). Where a session is opened and the person sent on — the end of `diluxone_users_complete_login()`, the end of the second step, and `login_redirect` at 99 for a password with no second step — the destination goes through `diluxone_users_ask_missing_url()`: while `diluxone_users_ask_missing` is on, a field is required and an account page is chosen, an account with no answer for a required field it may edit is sent to the account page with `diluxone-users-complete=1` and the destination in `redirect_to`. The account area draws `templates/fields.php` with those fields alone in place of its sections; its save is the account area's (`admin_post_diluxone_users_fields_save`) and goes on to the destination, checked with `wp_validate_redirect()`, once nothing required is missing. Nothing is stored and nothing is gated: no `template_redirect` check, a "Skip for now" link, and the question asked again at the next sign-in.
- **A Users+ Pro placeholder is the control it would be, switched off, and nothing else.** One pattern on every screen: the radio, tick box, button, card, shape or summary row the feature would be, drawn where it belongs, `disabled`, with the Pro pill and one "Learn about Users+ Pro" link (`diluxone_users_ui_pro_choice()`, `diluxone_users_ui_pro_button()`, `diluxone_users_ui_pro_card()`, `diluxone_users_ui_pro_shape()`, `diluxone_users_ui_pro_row()`, `diluxone_users_ui_pro_control()`). A control in it has no `name`, so nothing posts it whatever the browser is made to do; being disabled, a keyboard passes over it and a screen reader announces it as unavailable, and the link is what a keyboard lands on. All of them draw only in the admin, for whoever has `diluxone_users_admin_cap()`, while `diluxone_users_pro_previews` (a network setting) is on and `diluxone_users_upsell` says so for that place. The link goes out to diluxone.com and the plugin stops there: it never downloads or installs anything.
- **A page with a form, a second step or an account is never cached**: the chosen pages and any page carrying one of the shortcodes send `nocache_headers()` and define `DONOTCACHEPAGE` on `template_redirect`, and a shortcode drawn from elsewhere does it as it renders (`includes/no-cache.php`).

### WordPress conventions

- All user-facing strings go through translation functions with the text domain `diluxone-users`, with a `/* translators: */` comment on the line right before any placeholder. Eight locales are kept complete in `languages/`.
- **On a network the plugin is activated for the whole network, or it does nothing.** The header says `Network: true`, so WordPress offers only "Network Activate" and activating it from a site activates it for the network. The main file reads `includes/network-gate.php` first: `diluxone_users_awake()` is true on a single site and, on a network, only when the plugin is in the network's active plugins. A site it was left on for alone (an activation from before this rule, a copy dropped in by hand) loads nothing — no screens, no shortcodes, no sign-in — and shows whoever can `manage_network_plugins` a notice to activate it for the whole network, in Network Admin when the main site is one of those sites and on the dashboard of each of them. The activation hook is registered before the gate and loads the plugin itself, because WordPress runs it before it records the network activation. There is no per-site way of working on a network: each setting lives where its scope says (see Data below), the network's settings are set in Network Admin and nowhere else, and the main site is the hub whose sign-in, registration and account pages the network uses (the hub is always the main site in this version; see the hub's doors below). Users are network-wide, so anything that gives access calls `diluxone_users_join_site()`, which applies the network's membership policy (below).
- **On a network every door leads to the hub, and back** (`includes/network-hub.php`). A person's account lives on the hub: signing in, registering, the account area and social sign-in happen there and nowhere else, and so does an add-on's way in. On any other site (`diluxone_users_off_hub()`) the plugin's shortcodes draw a door to the hub instead of a form (`templates/hub-door.php`, through `pre_do_shortcode_tag`: a link, not a redirect, because the shortcode is one piece of a page the site wrote), the account's forms posted to that site go to the hub before their handler runs (`diluxone_users_hub_posts()`, which an add-on adds to), and social sign-in's `/sso/` route and its redirect URI are the hub's only. The account route was already the hub's (`diluxone_users_page_here()`). On a site that sends people to the hub (`diluxone_users_sends_to_hub()`: off the hub and not on a domain of its own), `diluxone_users_login_url()` and `diluxone_users_register_url()` carry `redirect_to`; WordPress's `login_url`, `register_url` and `lostpassword_url` are the hub's; and its wp-login.php is sent to the hub's at `login_init` priority 1 with the action and `redirect_to` kept — except what the site has to answer itself (`diluxone_users_wp_login_stays()`: `logout`, `postpass`, `confirmaction`, `rp`, `resetpass`, `enter_recovery_mode`, `confirm_admin_email`, the interim sign-in, the emergency `diluxone-users-admin` door, and any POST, which still meets the network's second step).
- **The way back is checked, held once and spent once.** A return address is an absolute http(s) address whose host is one of this network's sites (`diluxone_users_safe_return()`, built on the pure `diluxone_users_return_url_ok()`): no other host, nothing protocol-relative, no backslash, control character or user name, as typed or decoded. The network's domains are read from `wp_blogs` once and kept in a site transient that `wp_insert_site`, `wp_update_site` and `wp_delete_site` forget; `allowed_redirect_hosts` gets exactly those hosts, so a subdomain network can come back to `beta.example.com`. On the hub, the address arriving with its wp-login.php (`login_init` priority 2) or its sign-in and registration pages is held in a cookie, `diluxone_users_return`: HttpOnly, SameSite Lax, twenty minutes, never in a link or a mail. `diluxone_users_login_redirect` reads it at priority 5 (a site's own filter at 10 can still choose, and the confirmation of a personal-data request at 99 still wins): with no user yet (the password form being drawn) it only reads; for a user it spends it, runs `diluxone_users_join_site()` on that site (the membership policy decides what it adds), notes that site as where the sign-in came from (`diluxone_users_sign_in_from()`, for the log), and — when they are not a member of it — sends them back with `diluxone-users=join` so the page says so. A password posted to the hub spends it on `wp_login` (priority 1) the same way; WordPress's `login_redirect` adds the marker. An e-mail link opened in another browser has no cookie and lands on the hub's front page, signed in: accepted, not a bug.
- **Membership is the network's policy** (`includes/membership.php`, the network setting `diluxone_users_membership`, set on Network Admin › Membership, `includes/admin-membership.php`). `all` (the default): every account is a member of every live site of the network — a new account (`user_register`, `wpmu_new_user`, `wpmu_activate_user`, each re-applying it, since WordPress takes a new account's role on the current site away after `user_register`) is added to every live site, a new site (`wp_initialize_site` priority 20, after the plugin's own setup at 11) gets every account of the network, and signing in adds the current site and the hub. Any other policy is an add-on's (`diluxone_users_membership_policies`; Users+ Pro's `click` and `invite`): signing in adds the hub only, and a signed-in non-member of another site is told the site is by invitation (the menu, `[diluxone_users_join]`, and the box at the top of the page the hub sends them back to; `includes/membership-join.php`) unless the add-on answers a state of its own through `diluxone_users_join_state` and draws it (`diluxone_users_join_box`, `diluxone_users_join_link`). A stored policy nothing offers — one an add-on offered and is not running to apply, or a value nobody chose — reads as `hub` (`diluxone_users_membership_policy()`): signing in adds the hub only, new accounts and sites queue nothing, a job left in the queue is dropped, "Sync everyone now" adds nobody, a non-member is told the site is by invitation, and the screen says the policy is not active; it never reads as `all`, which would add every account to every site with no way back. Every addition goes through `diluxone_users_membership_add()`: never a super admin, a closed account, an archived, spam or deleted site, or somebody an administrator removed from that site; the role is the hub's registration role on the hub and the site's `default_role` elsewhere, subscriber when either fails `diluxone_users_role_self_serve()`; `diluxone_users_member_added` fires once per person and site in a request. An administrator's removal is written down on the person (user meta `diluxone_users_removed_from`, on `remove_user_from_blog`) and cleared when anybody adds them back (`add_user_to_blog`); removals nobody decided are not written down — a site being deleted (`wp_uninitialize_site`), an invitation being activated (`wpmu_activate_user`), an account being deleted (`wpmu_delete_user`), and the plugin's own, run inside `diluxone_users_membership_quietly()` (closing an account). Up to 50 additions (filter `diluxone_users_membership_inline`) are made on the spot; more are a job in the network setting `diluxone_users_membership_queue`, drained by the single cron event `diluxone_users_membership_drain` scheduled on the hub, ten batches of 200 additions (filter `diluxone_users_membership_batch`) a run, under a five-minute site-transient lock; a job left when the policy is no longer `all` is dropped, and a new site's job goes with the site when it is deleted (`wp_uninitialize_site`). **None of it runs until the network confirms the policy** (the network setting `diluxone_users_membership_confirmed`, `diluxone_users_membership_confirmed()`): until then `diluxone_users_membership_add()` refuses every addition but one a person asked for (`click`), new accounts and sites queue nothing, the queue waits untouched, "Sync everyone now" and the WP-CLI sync refuse, and Network Admin shows a notice everywhere but on the Membership screen, which asks for it ("Confirm the policy", the panel's `save_label`). The first save confirms; under `all` it then adds everybody already there (on the spot when small, through the queue when not). A network that ran the plugin before the setting existed starts unconfirmed too. "Sync everyone now" (a link that asks first, `manage_network_options`, nonce) and `wp diluxone-users network membership sync` queue an "everybody on every live site" job; the screen shows each job's progress. On a single site none of it exists: no screen, no handler, the shortcode draws nothing, and WordPress counts every account a member, so nothing is ever added.
- **Subdirectory and subdomain networks both work, because the session cookie is the network's.** On a subdirectory network WordPress sets it on the network's path, and on a subdomain network on the network's domain (`COOKIE_DOMAIN`, which WordPress defines for a subdomain install): a sign-in on the hub then reaches every site. A `wp-config.php` that pins `COOKIE_DOMAIN` to a single host breaks that, and the readme's multisite answer says not to. The plugin's own cookies use the same path and domain (`diluxone_users_cookie_set()`).
- **A site on a domain of its own is not supported in this version.** `diluxone_users_mapped_sites()` lists the sites whose domain is neither the network's nor a subdomain of it (the pure `diluxone_users_domain_is_mapped()`, ports included). The network's cookies do not reach them, so nothing is sent from them to the hub: their wp-login.php is their own, and people sign in again there — the sign-in shortcode's door on such a site (`templates/hub-door.php`, door `here`) leads to that wp-login.php and back to the page, not to the hub, whose session would never arrive. Network Admin's Overview names them and the site's own dashboard tells its administrator. There is no hand-off between domains.
- HTTP calls use `wp_remote_*` with an explicit `timeout`. Never raw cURL.
- Every `.php` file starts with `defined( 'ABSPATH' ) || exit;`.
- **PHP 8.0 and WordPress 6.2** are the minimums. No Composer dependencies at runtime.

### Data

- Renaming an option or a user meta key **requires a migration**, in a file of its own, run once and marked as done. There is none in the tree: the first release has nothing to migrate from.
- **Every stored setting has a scope** in `includes/options-scope.php`: `network` (who gets in and how safely: the second step, sessions, the proxy, the social credentials and linking rules, the fields, the log's retention, the wipe, the membership policy, its confirmation and its queue, whether the screens show where Users+ Pro would go), `hub` (the screens people sign in, register and keep their account on, and how they look and what they say) or `site` (the plugin's bookkeeping about the site it runs on). The activity log's own bookkeeping — the shape of its table — is `network`, because on a network the table is the network's. The map is explicit, key by key, and a unit test fails when a stored setting has no line in it. Settings are read and written only through `diluxone_users_option()`, `diluxone_users_raw_get()`, `diluxone_users_update_option()`, `diluxone_users_delete_option()` and `diluxone_users_save_options()`, never with `get_option()` and company on the plugin's own keys (the exception is `uninstall.php`, whose job is to see both places). On a network (`diluxone_users_scoped_storage_active()`, which is `is_multisite()`), a `network` setting is in the network's options (`get_site_option()`), a `hub` setting is in the hub's options table and read from any other site once per request, and a `site` setting stays with its site; on a single site everything is in the site's table. What fits into each site's own theme — the menu the account link goes in, the admin bar, the dashboard profile — is `site`. A hub setting that holds an id (the sign-in, registration and account pages; the pictures) is an id on the hub: `diluxone_users_page_url()` and `diluxone_users_hub_image_url()` resolve it there, and `diluxone_users_page_here()` is 0 on any other site, so another site never draws or routes one of its own pages as if it were the hub's.
- **Who writes what, from where.** `diluxone_users_admin_context()` says where the admin is looked at from — `single`, `network` (Network Admin), `hub` or `site` — and `diluxone_users_save_options()` writes only the settings that context owns (`diluxone_users_option_editable_here()`): Network Admin writes the network's, the hub its own and the site's, another site only its own. Every screen's save goes through it, so a site administrator cannot change or loosen a network setting by sending a form by hand. The screens follow the same map (`admin-network.php`): each screen and tab has a scope, the network's are drawn in Network Admin with `manage_network_options` and leave every site's menu, and a site's Overview says where each area went.
- **The activity log on a network** (`includes/log.php`). On a network the log is one table, `{$wpdb->base_prefix}diluxone_users_log`, and every row carries `site_id` (indexed `site (site_id,id)` and `site_when (site_id,happened)`); its shape marker `diluxone_users_log_schema` is a network setting, and the table is made once for the network when the first group to record is ticked (by the first write, or by `admin_init`), never on activation; a site makes no table of its own on a network. A single site has the same name — its prefix is the base prefix — and the same columns: one writer, one set of queries, the site being one more filter (`diluxone_users_log_search()`'s `site`, built into the WHERE only when set). Any read or write first checks the shape (`diluxone_users_log_current()`) and brings a table a shape behind up to date, so an update over FTP never queries a column that is not there yet. A site's report and its "Empty it now" are that site's rows — the report also lists the sign-ins on the hub that came from that site: a `signed_in` row written on the hub for another site carries `from_site` in its detail, and a site's report asks for `site_id = site OR ( event = 'signed_in' AND detail LIKE '%"from_site":"site"%' )` (`diluxone_users_log_search()`'s `arrivals`, on a network only); Network Admin › Activity log has every site's rows, a Site column and filter, a From column (the site a sign-in on the hub came from), and an "Empty it now" for every row (`manage_network_options`). The daily purge runs on the main site only, with the network's retention, over every row of the network's sites. Erasing a person is one query on the table; taking somebody off one site (`deleted_user` on a network) takes only that site's rows; a deleted site takes its rows (`wp_uninitialize_site`) and any old table of its own (`wpmu_drop_tables`, never the network's). One table serves every network of a multi-network install, so whatever a network does to its rows it does to its own sites' rows only (`diluxone_users_log_network_sites()`, the current network's site ids through `get_sites()`, used in groups of 500 for an `IN ( … )`): its report and its Site filter, its "Empty it now" and its purge never touch another network's rows. Erasing a person is the exception and stays installation-wide, because a person is.
- Field keys are user-visible configuration: once a field exists, its key does not change, because the key is also the meta key holding everybody's answer. Under the plugin's prefix a field takes a key only in the fields' own corner, `diluxone_users_field_` (`DILUXONE_USERS_FIELD_PREFIX`, where `diluxone_users_key_from()` makes every new one), or one a field already had before the corner existed, or a suggested field's (`diluxone_users_field_key_ours()`); the rest of the prefix is somebody's data.
- **The `diluxone_users_` namespace is the plugin's, and it is accounted for by its prefix, not by a list of names.** An add-on (DiluxOne Users+ Pro is one) stores its settings and its user meta under it, and may not be running when the plugin reads, saves, exports, erases or uninstalls: so its settings join through `diluxone_users_option_defaults` and `diluxone_users_option_scope` (only keys under the prefix that the plugin does not have), a field cannot be named after its meta (above), the privacy eraser takes every `diluxone_users_%` and `_diluxone_users_%` key a person has but the two kept on purpose (`diluxone_users_removed_from`, `diluxone_users_closed`), the exporter lists every key nothing explained by name with its value withheld (`diluxone_users_privacy_keys`, `diluxone_users_privacy_export_items`), and `uninstall.php` deletes options and user meta by prefix. A list of an add-on's keys written into this plugin is the thing to avoid: the day the add-on's keys change, the list is wrong.
- **A save writes what its screen drew and keeps what it does not know.** A value whose control was not on the screen is not written (`diluxone_users_panel_drawn()`: it arrived, or a tick box said it was drawn through `diluxone_users_panel_drawn[]`, which `diluxone_users_ui_choice()` prints), and a save that writes a list or a map merges with what is stored and keeps the entries it does not recognise — a provider's row, a second factor nothing registers, a section of the site's own.
- **A stored choice nothing offers today is kept, and replaced on the front end by the closest free one.** A sign-in shape nothing draws is the card; an account shape, the simple one; a colour none of the short palettes has (one chosen while an add-on made any colour an answer), the palette's nearest measured in OKLab, or the default when that one would not read (`diluxone_users_palette_color()`), and on its screen "Your Pro colour (inactive)"; a membership policy, the hub only (above); a second factor nothing registers is asked of nobody. On its screen the choice is drawn chosen and marked as an inactive Pro choice after the real answers (`diluxone_users_ui_kept()`, `diluxone_users_ui_kept_card()`), and the save keeps it until another answer is picked (`diluxone_users_unknown_choice()`, `diluxone_users_choice_kept()`, `diluxone_users_unknown_entries()`). A word nobody offered, sent by hand, is still the default.
- `uninstall.php` wipes only when an administrator asked for it beforehand (Maintenance → Tools on a single site; Network Admin → Overview → Deleting the plugin on a network); otherwise deleting the plugin keeps people's data. On a network it is that one decision: ticked, the network's options and its activity log, every site's settings and the plugin's user meta go. WordPress's own user meta keys (`diluxone_users_core_user_meta()` in `includes/core-meta.php`, the list a field's name is also checked against, and anything under the table prefix) are never deleted, on either topology, even when a stored field carries one: a field keyed `description` would otherwise take every biography with it. A box a site ticked for itself never counts.

## Deliberate style choices

Do not comment on these in a review.

- **Yoda conditions** in comparisons against literals (`'' === $value`), following WPCS.
- **Procedural code with a `diluxone_users_` prefix** is the convention. Do not suggest wrapping it in classes.
- **Comments explain decisions, not mechanics.** A comment that says what the next line does is noise; one that says why the obvious alternative was rejected stays.
- **Native types instead of `@param` lines.** The signatures are typed; the docblock explains why the function exists and documents array shapes in `@return`. The PHPCS configuration relaxes that rule on purpose.

## What a review looks for

- **Missing escaping on output**, especially in `templates/`.
- **Missing unslash + sanitize on input**, especially in new admin handlers.
- **A single-use token that stops being single use**, or a secret stored or logged in the clear.
- **A new screen or panel that shows something the settings say is off.**
- **A new section without `available` / `why`** that can render empty.
- **A new option that no screen exposes**, or a screen control that saves nothing.
- **Renaming a stored key without a migration.**
- **Anything that makes the plugin depend on another plugin** without a `function_exists()` guard.
- **New strings not wrapped in a translation function.**
- **`$wpdb` queries inside loops**: suggest batching.
- **A redirect, a door or a step that ignores `diluxone_users_safe_mode()`**, or a second step that can be required with nowhere to answer it.
- **A sign-in that opens a session without `diluxone_users_open_session()`**: it would skip `wp_login`.
- **A change without its tests** at the layers it touches ([`testing-and-quality.md`](testing-and-quality.md)).

The paths where a mistake locks people out, lets the wrong person in or leaks their data are listed in [`.github/review-policy.yml`](../.github/review-policy.yml): a change there is always high risk and always merged by a person.
